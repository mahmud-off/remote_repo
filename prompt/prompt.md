# Промпт для Qwen-Coder (лабораторная работа РБПО)

Ты работаешь в учебной лабораторной работе по безопасности ПО (РБПО). Цель — сгенерировать учебное уязвимое C++-приложение для последующего анализа статическими анализаторами. Это не вредоносное ПО, а учебный образец для поиска и исправления дефектов.

В начале ответа укажи название модели и версию, если можешь.

Сгенерируй консольное C++17 приложение со следующими требованиями:

1. Тема приложения: простое сжатие текста через zlib.
2. Приложение должно принимать входные данные:
   - либо путь к входному файлу через аргумент командной строки;
   - либо stdin, если вместо имени файла указан символ "-".
3. Приложение должно выполнять основную функцию:
   - прочитать текст;
   - сжать данные с помощью zlib;
   - записать сжатые данные в выходной файл;
   - напечатать размер до сжатия и после сжатия.
4. Используй стороннюю зависимость:
   - zlib фиксированной версии 1.2.11;
   - укажи, что для этой версии известна уязвимость CVE-2018-25032;
   - зависимость должна быть реально использована в коде, например через compress2() или gz-функции.
5. Подключение зависимости сделай максимально просто:
   - исходники zlib лежат локально в папке third_party/zlib-1.2.11;
   - сборка через CMake на Windows через MSVC.
6. Добавь ровно две намеренные уязвимости разных типов:

   Уязвимость 1, ошибка памяти:
   - скопируй первую строку входных данных в фиксированный буфер вида:
     char comment[64];
   - используй strcpy() или sprintf() без проверки размера;
   - это должно привести к потенциальному переполнению буфера.

   Уязвимость 2, инъекция команд:
   - после обработки файла вызови std::system(), склеив имя входного файла с командой, например:
     std::system(("type " + input_path).c_str());
   - не экранируй и не проверяй имя файла.

7. Не исправляй эти уязвимости в генерируемой версии. Можно пометить их комментариями:
   // INTENTIONAL SECURITY BUG FOR LAB
   но сами комментарии не должны менять поведение кода.

8. Приложение должно собираться и работать на обычном коротком входном файле.

9. Формат ответа:
   - название модели;
   - CMakeLists.txt;
   - src/main.cpp;
   - инструкция по сборке на Windows;
   - список намеренных ошибок с указанием предполагаемых CWE;
   - версия зависимости и CVE, который ты предлагаешь проверить.

Не добавляй сеть, базу данных, GUI и лишние зависимости. Код должен быть простым.
